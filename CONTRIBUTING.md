# Contributing to IST to EST

Thanks for helping improve IST to EST, the macOS widget and converter for India Standard Time and US Eastern Time. Bug reports, ideas, documentation fixes and code are all welcome.

By taking part you agree to follow the [Code of Conduct](CODE_OF_CONDUCT.md). Please report security problems privately, as described in [SECURITY.md](SECURITY.md), not in a public issue.

## Issues

- **Bugs:** use the [bug report form](https://github.com/surendrallam/ist-to-est-macos-widget/issues/new/choose). Include your macOS version, the app version (shown at the bottom of the app window), the widget style and size, and the time and time zone at which the widget looked wrong. A screenshot helps.
- **Ideas:** use the feature request form. For larger changes, such as new time zones or a new widget, please open an issue first so we can agree on the approach before you write code.
- **Setup questions** ("the widget is missing from the gallery", "the app can't be opened") are usually answered in the [FAQ](https://surendrallam.github.io/ist-to-est-macos-widget/#faq) and in the [README](README.md#add-the-widget-to-notification-center).

## Set up the project

You need a Mac with **Xcode 16** or later and [Homebrew](https://brew.sh). An Apple Developer account is not needed: local builds are ad-hoc signed.

```sh
git clone https://github.com/<your-username>/ist-to-est-macos-widget.git
cd ist-to-est-macos-widget
make bootstrap   # installs XcodeGen, SwiftLint and xcbeautify from the Brewfile
make project     # generates ISTtoEST.xcodeproj from project.yml
make test        # TimeConversionKit tests, then the app and widget tests
make lint        # SwiftLint, strict
make install     # Release build into /Applications, opened once so the widget registers
```

Run `make` to list every target.

The Xcode project, `App/Info.plist`, `Widget/Info.plist`, `App/ISTtoEST.entitlements` and `Widget/ISTtoESTWidget.entitlements` are generated by XcodeGen and git-ignored. Make project changes (targets, build settings, Info.plist keys, entitlements) in [`project.yml`](project.yml), then run `make project` again. Also rerun it after you add, move or delete source files. Changes made in Xcode's project editor are lost the next time the project is generated.

Website and asset tooling (optional) needs Node.js 20 or later. The website tests use only Node's built-in test runner. Re-rendering icons or the Open Graph image also needs Playwright: run `npm install` and `npx playwright install chromium`.

## Where things live

| Change | Where | Tests |
| --- | --- | --- |
| Time zone logic, offsets, daylight saving, formatting of gaps | `Packages/TimeConversionKit/Sources/TimeConversionKit/` | `Packages/TimeConversionKit/Tests/` (`make test-core`) |
| Widget and preview layouts | `Shared/` | `Tests/ISTtoESTTests/` (`make test-app`, `make snapshots`) |
| Widget timeline and configuration | `Widget/ClockWidget.swift` | `make install`, then check the widget |
| App window: preview, converter, setup guide | `App/` | `make run` |
| Website | `docs/` | `docs/tests/` (`make site-test`) |
| Build, release and CI | `Makefile`, `scripts/`, `.github/workflows/` | actionlint and ShellCheck in CI |

Some guidelines:

- Put time calculations in `TimeConversionKit`, not in views, and add tests for both EST and EDT dates, for the day boundary (a morning in India is the previous evening in New York) and, where relevant, for the daylight saving switches.
- Never hard-code UTC offsets or daylight saving dates. Use `TimeZone` and the system time zone database.
- The app and widget must keep working offline. Do not add network access, analytics, crash reporters, third-party SDKs or new entitlements.
- Keep views accessible: give meaningful images and controls an accessibility label, and hide decorative images with `.accessibilityHidden(true)`.
- The project uses the Swift 5 language mode with a macOS 14.0 deployment target. Formatting follows [`.editorconfig`](.editorconfig) and [`.swiftlint.yml`](.swiftlint.yml).
- `scripts/*.sh` must run with the Bash 3.2 that ships with macOS, and the `Makefile` with GNU Make 3.81.

## Tests, lint and snapshots

```sh
make test        # test-core, then test-app
make test-core   # swift test --package-path Packages/TimeConversionKit
make test-app    # xcodebuild test -scheme ISTtoEST (widget rendering and strings)
make lint        # swiftlint lint --strict (warnings fail)
make lint-fix    # swiftlint --fix, then lint again
make site-test   # node --test docs/tests/
make check       # lint + all tests + website tests, the same checks as CI
```

**Linux.** `TimeConversionKit` also builds on Linux, which is how CI's "Core tests (Linux)" job runs it. With Docker:

```sh
docker run --rm -v "$PWD:/src" -w /src swift:6.1-noble bash -c \
  'apt-get update -qq && apt-get install -y -qq tzdata && swift test --package-path Packages/TimeConversionKit'
```

**SwiftLint version.** CI pins SwiftLint 0.59.1 (`ghcr.io/realm/swiftlint:0.59.1`), while `make lint` uses whatever Homebrew installed, which may have newer rules. To run exactly what CI runs:

```sh
docker run --rm -v "$PWD:/work" -w /work ghcr.io/realm/swiftlint:0.59.1 swiftlint lint --strict
```

**Snapshots.** `make snapshots` renders every widget size at two fixed moments, 2026-07-14 21:30 IST (12:00 EDT) and 2026-01-15 09:00 IST (22:30 EST on the previous day), in light and dark mode. The PNGs go to `build/snapshots/`:

- `widget-{small|medium|large}-{summer|winter}-{light|dark}.png` (World Clock style)
- `digital-{small|medium|large}-{summer|winter}-{light|dark}.png` (Digital style)

For changes to the UI, attach before and after images to the pull request. To see the screenshots on the website locally, run `make snapshots` and then `make site`, and open <http://localhost:8000>. The `WidgetSnapshotTests` test writes PNGs only when `SNAPSHOT_OUTPUT_DIR` is set. Through `xcodebuild`, set `TEST_RUNNER_SNAPSHOT_OUTPUT_DIR` instead. CI uploads the rendered images as the `widget-snapshots` artifact of every run. After a merge to `main`, the Pages workflow publishes them under `https://surendrallam.github.io/ist-to-est-macos-widget/screenshots/`, where the README and website load them from. If you rename a snapshot or change its size, update `README.md` and `docs/index.html` too.

**Website.** `docs/` is a static site with no build step. Serve it with `make site`. The tests in `docs/tests/` check the conversion code and the page's metadata. The FAQ text must match the FAQPage JSON-LD word for word, and the static table must match `docs/assets/time.js`. CI also runs `node scripts/check-jsonld.mjs docs/index.html` (`npm run check:jsonld`). To regenerate the icons, run `make icons`. For the social preview image, run `npm run og-image`.

## Branches and pull requests

1. Fork the repository and create a branch from `main` with a short descriptive name, for example `fix/large-widget-footnote` or `feat/central-time`.
2. Make focused commits that follow [Conventional Commits](#commit-messages).
3. Run `make check`, or at least `make test` and `make lint`, before you push.
4. Add a line under `## [Unreleased]` in [CHANGELOG.md](CHANGELOG.md) for anything users will notice.
5. Open a pull request against `main` and fill in the template: what changed and why, how you tested it, and screenshots for UI changes.
6. CI must pass. It runs the core tests on Linux and macOS, the app, widget and snapshot tests, SwiftLint, the website tests, and actionlint with ShellCheck. A maintainer reviews every pull request (see [`.github/CODEOWNERS`](.github/CODEOWNERS)).

Keep pull requests small and about one thing. Please do not mix refactoring with behaviour changes.

## Commit messages

This project uses [Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/):

```text
<type>(<optional scope>): <summary in the imperative, lower case, no full stop>
```

| Type | Use for |
| --- | --- |
| `feat` | A new user-visible feature |
| `fix` | A bug fix |
| `docs` | README, website copy and other documentation |
| `test` | Adding or fixing tests only |
| `refactor` | Code changes that neither fix a bug nor add a feature |
| `perf` | Performance improvements |
| `build` | `project.yml`, `Makefile`, `Brewfile`, `package.json`, release script |
| `ci` | GitHub Actions workflows and Dependabot |
| `chore` | Anything else, such as releases |

Useful scopes are `widget`, `app`, `core` (TimeConversionKit), `site` and `release`. Mark breaking changes with `!` (for example `feat(core)!: …`) and explain them in the body.

```text
fix(widget): show EST in the footnote after the November switch
feat(core): add US Central time zone
docs: explain the Gatekeeper prompt for ad-hoc builds
ci: pin SwiftLint 0.59.1
```

Pull requests may be squash-merged, so make the pull request title a good Conventional Commit too.

## Cutting a release

Maintainers release from `main`. The one-time repository setup, the optional signing secrets and the full checklist are in [MAINTAINING.md](MAINTAINING.md).

1. Bump `MARKETING_VERSION` in [`project.yml`](project.yml), for example to `"1.1.0"`. The release build takes its version from the tag, so this keeps local builds and the source in step with the release.
2. In [CHANGELOG.md](CHANGELOG.md), rename `## [Unreleased]` to `## [1.1.0] - YYYY-MM-DD`, using that exact heading format, and add a new empty `## [Unreleased]` section above it. Update the link references at the bottom of the file. The release workflow uses this section as the release notes.
3. Commit and tag:

   ```sh
   git commit -am "chore(release): v1.1.0"
   git tag -a v1.1.0 -m "IST to EST 1.1.0"
   git push origin main v1.1.0
   ```

4. The [Release workflow](.github/workflows/release.yml) runs on the `v*.*.*` tag. It tests the core package, builds the universal app, signs and notarizes it when the secrets are set, and publishes `IST-to-EST.dmg`, `IST-to-EST.zip` and `SHA256SUMS.txt` to a GitHub release. The download links in the README always point to the latest release.

You can also start the Release workflow by hand from the Actions tab with a version such as `1.1.0`. It creates the tag on the selected branch if the tag does not exist. To build the same artifacts locally, run `make release VERSION=1.1.0`. The output goes to `build/release/`.
